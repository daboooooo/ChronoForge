### 2.1 官方发布时刻（以官方页面为准）

### 2.2 项目侧更新时刻与可靠性判断

**已统一为单一批次**：`config/update_schedule.py` 只保留 `DAILY_UPDATE_TIME_UTC = (7, 40)`（北京时间 15:40 = 07:40 UTC），不再有 source 级 / dataset 级分散发布时刻；`backfill_datasets.py::_next_due_at` 对日频及以上数据集一律对齐该批次。

| 数据集 / 源 | 项目配置 | 可靠性判断 |
|---|---|---|
| 全部日频及以上数据集 | `DAILY_UPDATE_TIME_UTC=(7,40)`，由 `scripts/hourly_update.sh daily` 触发全量刷新 | **不是官方发布时刻，而是抓取批次时刻**。07:40 UTC = 03:40 ET（夏令时）/ 02:40 ET（冬令时），在美股开盘前，抓到的必然是上一完整交易日的数据 |
| 子日频（1h/4h） | `hourly_update.sh loop` 整点轮询 `--due-only` | 只为加密等高频序列服务；不参与日报的 T-1 基准，写锁与 daily 批次共享 |
| Treasury DTS（PIT） | `TREASURY_DTS_RELEASE_TIME_UTC=(21,0)`，仅用于 canonical `release_time` | 与官方"次一工作日 16:00 ET"一致；21:00 UTC 是保守跨日时点。**与抓取批次解耦**：批次提前抓取不改变"何时公开可用"的语义 |
| NY Fed SOMA / SRF | 不再有 dataset 级发布时刻；统一走 07:40 批次 | 连接器的 `release_time` 常量（SOMA 周四 23:59:59 UTC、SRF 22:00 UTC）只作 PIT 保护，不作为抓取时刻；报告 as-of 以实际观测日期为准。Phase 0 已核实官方时刻：SRF 操作日约 13:45 ET、SOMA 随 H.4.1 周四 16:30 ET；现有常量偏保守（见 V3） |
| Yahoo / 行情 | 统一走 07:40 批次 | 07:40 UTC 晚于上一交易日收盘（20:00/21:00 UTC），日线已完整；仍须丢弃任何未完成 bar |

> **结论**：批次时刻只能作为"抓取调度"，不能当作"官方发布时刻"写进报告。报告的所有 as-of 必须由**实际观测日期**反推，不能由常量假设；`daily_update.json` 只证明"批次跑过"，不证明"每个数据集都拿到了最新值"。

设报告日为美东交易日 T（北京日期同为 T）。16:00 北京 = 03:00 ET（EST）/ 04:00 ET（EDT）。以下为"当天这一时刻实际能看到的最新时点"：

| 数据 | 周一 | 周二 | 周三 | 周四 | 周五 | 说明 |
|---|---|---|---|---|---|---|
| 美股/ETF 行情 | 上周五收盘 | 周一收盘 | 周二收盘 | 周三收盘 | 周四收盘 | 最新完整日线 = T-1 |
| 加密日线 | 周日 00:00 UTC | 周一 00:00 UTC | 周二 00:00 UTC | 周三 00:00 UTC | 周四 00:00 UTC | 24/7；周一报告可用周末走势，但须丢弃当日未完成 bar |

### 2.4 调度时序：原缺口与单批次修复

**原缺口（已修复）**

- `hourly_update.sh` 原为整点轮询，FRED 配置 08:10 UTC：08:00 轮询时尚未到期，09:00 才抓；而报告在 08:00 UTC，只能读到**前一天 09:00 抓取的版本**。
- 更严重的是 09:00 UTC 抓取仍早于 EFFR/SOFR 发布（约 13:00/14:00 UTC），`--due-only` 以 `last_success_time` 推进 checkpoint，把"已抓但仍是旧值"固化；报告因此可能看到 **T-3**，而不是理论上限 T-2。

**单批次修复（当前实现）**

| 项 | 做法 | 效果 |
|---|---|---|
| 批次时刻 | `DAILY_UPDATE_TIME_UTC=(7,40)`，`hourly_update.sh daily` 在 15:40 北京全量刷新 | 批次与报告（16:00）只隔 20 分钟；报告读的是本批次完成后的状态 |
| 报告前置条件 | `daily` 完成后原子写 `var/run/daily_update.json`（`status=ok/partial/timeout/blocked/failed`） | 报告以文件为门禁，不再只按日历时刻硬碰；失败/超时用最近成功批次并显式标注 as-of |
| EFFR/SOFR | 07:40 批次重新抓取（此时最新可用为 T-2） | 从"前一天抓取导致的 T-3"回到 T-2；**T-2 即理论上限** |
| 子日频数据 | `loop` 仍逐小时 `--due-only`，写锁每轮短持有 | 保留加密等采集能力，日报不被整小时锁挡住 |

> **决策**：原方案 A（按数据集拆分 07:55 / 12:30 / 13:30）**已取消**。单批次更简单，且不存在"定时时刻与实际发布错配"的缝隙；代价是 EFFR/SOFR 固定在 T-2，但这本来就是 16:00 报告的结构性上限。若未来把报告改到晚间（例如 21:00 北京），再重新评估批次时刻。

### 2.5 时效结论

1. **16:00 北京无法拿到"当天"美国数据**，这是时区决定的事实；报告应称为"盘前简报"，以 T-1 收盘和 T-2 资金面为基准。
2. **周频数据不是"每天更新"**：H.4.1/H.8/SOMA 的周四/周五节奏决定了周二–周四报告使用上周数据；报告必须显示"下一次发布"与"待纳入"。
3. **TGA 日值是 T-2**：DTS 次一工作日 16:00 ET 发布，报告在 T 16:00 北京（T 03:00/04:00 ET）早于发布。TGA 的"当前"只能用官方 T-2 + 模型情景路径表达，不能写成"今日 TGA"。
4. **SOFR/EFFR 是 T-2，且 T-2 是理论上限**：T-1 的利率在 T 08:00/09:00 ET 发布，报告（T 03:00/04:00 ET）早于发布。单批次 07:40 UTC 在报告前重新抓取，稳定兑现 T-2；这不是调度缺陷，除非报告改到晚间才可能拿到 T-1。
5. **加密是唯一有"周末/亚洲时段"增量的风险信号**：周一报告可以用周日/周一凌晨的加密走势补足美股闭市期间的风险偏好，但必须标注 as-of 08:00 UTC，并丢弃未完成日线。

## 3. 触发时间与交易日口径

### 3.1 触发时间决策

| 选项 | 时点 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 北京 16:00（美东 03:00/04:00） | 盘前 5.5–6.5 小时，可读、可行动；与用户要求一致 | 当日美国数据未发布；SOFR/TGA T-2 | **采用** |
| B | 北京次日 06:00（美东 17:00/18:00） | 当日收盘、TGA T-1、EFFR/SOFR T-1 都可拿到 | 变为"收盘复盘 + 次日展望"，不再是盘前 | 备选，不采用 v1 |
| C | 16:00 盘前 + 次日 06:00 收盘双版 | 兼顾速度与完整 | 双倍产物、双倍维护 | 不推荐 v1 |

**采用 A 的理由**：报告的核心用途是"在美股开盘前形成当日流动性判断"，而不是"复盘当天已发生的一切"。盘前 5–6 小时恰好覆盖亚洲时段与欧洲早盘，读者有时间调整仓位/观察清单。为此接受 T-2 的资金面滞后，并在报告中显式标注。

### 3.2 交易日口径

- **复用** `src/chronoforge/quality/calendar.py` 的 `is_trading_day` 与假日表（2021–2027），**不另建日历**。
- 报告日判定：以触发瞬间的 `America/New_York` 日期 `us_date` 为准；在 16:00 北京时 `us_date == 北京日期`。若不等（理论上不会），以 `us_date` 为准。
- **非交易日**：`is_trading_day(us_date) == False` → 记日志并 `exit 0`，不生成报告。北京周六 16:00 对应美东周五凌晨（交易日），但北京周六不是"美股交易日"口径；以 `us_date` 判定即可自然排除。
- **半日市**（感恩节次日、圣诞前夕等）：`is_trading_day` 仍为 True，报告正常生成；在 metadata 标记 `early_close=true`、`early_close_time=13:00 ET`，并在"风险/日历"中说明下一交易日的完整收盘时点。
- **假日表覆盖**：`calendar.py` 当前覆盖到 2027；2027 年后 `is_trading_day` 会抛 `ConfigError`。调度器必须捕获并以非零退出报警，不能静默跳过；每年 Q4 维护下一年假日表（列入运维清单）。
- **`EARLY_CLOSINGS` 覆盖**：需在 Phase 0 核对 2026–2027 是否完整；缺失时仅影响"半日市标注"，不影响交易日判定。

### 3.3 报告日期与 as-of 命名

- 文件名日期 = **美股交易日 T**（与北京日期一致）。
- 标题写"YYYY-MM-DD（周X）盘前"。
- 每个数据块写"截至 YYYY-MM-DD"或"最新可得 YYYY-MM-DD（T-2）"。
- **禁止**在滞后指标旁使用"当前/今日/实时"；由校验器检查（见 §5.4）。

**视觉规范**

- 深色主题（与现有 Dashboard 一致），打印时切换浅色；主色青/蓝，警戒琥珀，压力红；不引入 3D、仪表盘、无意义渐变。
- 每张图必须有：标题、as-of 徽章、单位、来源脚注、最新值直接标签。
- 图表数据全部内联在 HTML 的 `window.CF_REPORT_DATA` 中；ECharts 使用本地 `assets/echarts.min.js`，离线可开。
- 响应式：桌面双列、移动单列；关键 KPI 在首屏 4 卡（准备金水位/4w 变化、TGA、RRP、SOFR-EFFR）+ 状态徽章（流动性/宏观/数据完整度）。

### 4.3 文字说明的重点

- **开头 3–5 条结论**：每条必须是"数字 + 方向 + 含义 + 引用"，例如"准备金 3.02T，4 周 -X B，处于 3.0–3.2T 预警区下沿 [F-12][REL_022]"。
- **历史段**：先给水位与趋势，再给分解（谁抽水/谁注水），最后给资金面验证（价格是否确认数量变化）。
- **前瞻段**：必须写"状态 → 机制 → 路径 → 触发 → 失效"五段式（见 §6.2），不能只写"未来可能收紧"。
- **风险段**：每条风险都有证据、传导链、触发条件、失效条件、下一观察点；不写无法证伪的泛泛之谈。
- **数据段**：把"为什么这个指标是 T-2"写清楚，让读者知道不是数据坏了，而是发布节奏。

## 5. 确定性与模型边界

### 5.1 确定性计算（代码负责，LLM 不得改）

| 类别 | 内容 | 来源/公式 |
|---|---|---|
| 水位与变化 | 准备金、WALCL、TGA、RRP、SRF、流通货币；1d/1w/4w/13w | `build_payload()` + 原始序列 |
| 分位 | 5y/10y 滚动分位；变化的分位 | 报告层新增，样本窗口与缺失处理写进附录 |
| 利差/走廊 | SOFR-EFFR、EFFR-IORB、ON RRP 利率与 EFFR 差 | `build_payload()` 的 `corridor` |
| 周度分解 | WALCL − TGA − RRP − 流通货币 − 其他 ≈ Δ准备金 | 复用 `build_payload()` 的 `weekly.decomp`；标注"残差" |
| 状态 | 流动性区（充足/正常/预警/紧张）、宏观 A–D | 复用 `build_payload()` 的 `status` |
| 阈值 | 准备金 3.0/3.2T；SOFR-EFFR 12/17bp；SRF 3B；RRP 50B；TGA 周增 50/100B | KB `REL_007`、`REL_010`、`VAR_ON_RRP`、`REL_015`；阈值集中到 `config/daily_liquidity_report.yaml` |
| 预测 | TGA 7/14/30 情景、准备金 1/2/4 周 + 90% 带 | `derived/tga_forecast`、`derived/reserve_forecast` |
| 风险规则 | 已触发/潜在风险、监控清单 | `report/rules.py`，每条规则可单测 |
| 日历 | 发布日、拍卖结算、税期、月末/季末、半日市 | `calendar.py` + `config/tga/calendar.yaml` + `treasury_auctions_upcoming` |
| 昨日复盘 | 昨日判断是否命中 | 读取 `YYYY-MM-DD.json` 的 `judgments`，用今日实际值判定 |

### 5.2 LLM 只做文字

- **输入**：`facts.json`（紧凑版，不含原始长序列）+ 选中的 KB 片段（`VAR_*` / `REL_*` / `KP_*` / `CASE_*`）+ 昨日 `judgments` + 输出 schema。
- **输出**：结构化 JSON（`summary`、`history_current`、`outlook`、`risks`、`watchlist`、`scorecard`、`data_gaps`），每段带 `citations`。
- **模型**：OpenAI-compatible HTTP（`httpx` 已在依赖）；配置 `CHRONOFORGE_LLM_BASE_URL` / `CHRONOFORGE_LLM_API_KEY` / `CHRONOFORGE_LLM_MODEL` / `CHRONOFORGE_LLM_TIMEOUT_S`。没有配置时直接走模板，不报错。
- **不在 LLM 输入里放**：原始 5–10 年序列、数据库连接、内部文件路径、API key。
- **可复现**：JSON 里记录 `model`、`temperature`、`prompt_hash`、`facts_hash`、原始输出、校验结果；HTML 只展示校验后的文本。

### 5.3 防编造数字

1. **数字白名单**：从 `facts.json` 提取所有数值（含单位换算后的等价形式），生成 `allowed_numbers`；生成文本中的每个数字 token 必须能匹配到白名单（允许四舍五入/千分位/中文单位）。
2. **引用必填**：每段至少一个 `citation`，ID 必须存在于 `kb_refs` 或 `facts`；未知 ID → 拒绝。
3. **禁止新风险/新因果**：`risks` 只能引用 `risk_id`；`outlook` 的机制必须引用 `REL_*`/`KP_*`；出现未列出的风险名称 → 拒绝。
4. **禁止伪概率**：除非 `facts` 里有明确的历史命中率/回测数字，否则不允许"70% 概率""大概率"等表述；统一用"若…则…"条件句。
5. **时点词校验**：对 `LAGGED_BY_DESIGN` 的指标，禁止"当前/今日/实时"；必须写"截至…"。
6. **失败降级**：校验失败 → 带错误重试 1 次 → 仍失败 → 模板叙事；`narrative_mode="template"` 写入 JSON/HTML，不清空报告。

### 5.4 防"每天雷同"

| 机制 | 做法 |
|---|---|
| 昨日计分卡 | 每天把昨日的可证伪判断（指标/算子/阈值/期限）用今日数据判定 `hit/miss/pending`，写进"昨日复盘"；这是最强的差异化 |
| 变化引擎 | 计算 `top_changes`：水位、利差、阈值穿越、预测修订、风险旗标、日历事件；要求开头必须写 3 条变化，或明确"无实质变化"并解释 |
| 编辑日历 | 周一"周度重置 + H.8"；周二"资金面/TGA"；周三"拍卖结算"；周四"H.4.1 待发布"；周五"H.4.1 新数据"；不同日不同 lens |
| 新颖度检查 | 与最近 3 篇的句子 Jaccard/字符 n-gram 相似度；>0.75 则重写一次，仍高则用"无实质变化 + 今日新增证据"模板 |
| 可证伪要求 | 每篇 `outlook` 至少 1 条"指标 + 算子 + 阈值 + 期限"的判断；否则校验失败 |
| 禁止复读 | 不允许整段复用昨日段落；模板也按 `top_changes` 重新组装 |

### 5.5 前瞻的论证结构（五段式）

每条前瞻判断必须按以下结构写入 `facts.outlook.calls[]`，LLM 只能扩写：

1. **状态**：当前水位/趋势/资金面/市场状态（带 as-of）。
2. **机制**：KB 中的数量关系或事件驱动（引用 `REL_*`/`KP_*`，标注证据等级：SOURCE / accounting_identity / author_claimed / hypothesis）。
3. **路径**：TGA 情景 + 准备金预测的 1/2/4 周数值区间（来自模型，不是 LLM 编的）。
4. **触发/验证**：下一个 H.4.1/DTS/拍卖/阈值，什么数据会确认。
5. **失效**：什么数据会证伪（例如准备金反弹、RRP 重建、TGA 回落、利差回落）。

> 示例（仅示意结构，不是预测）：
> "若下周 H.4.1 准备金跌破 3.0T，且 SOFR-EFFR 连续 3 日 > 12bp，则 SRF 用量可能升破 3B；验证点是下周 H.4.1 与每日 SRF；失效条件是 RRP 重建或 TGA 回落。"
>
> 这样写出的前瞻是可检验的，而不是"未来可能偏紧"。

16:00 北京触发报告

  → 前置闸门：读 daily_update.json（ok/partial 继续；timeout/blocked/failed/缺失

- 覆盖策略：同一天默认原子覆盖；`--keep-history` 时保留 `YYYY-MM-DD.rN.json`。JSON 里的 `revision` 与 `generated_at` 保证可追溯。
- **与现有站点的关系**：`visualization/index.html` 仍是交互式全量 Dashboard；`docs/USD_Liquidity/index.html` 仍是知识库；日报是第三层"每日决策简报"。日报链接到两者（相对路径），不修改两者；如需发布，只在 Dashboard/知识库增加"最新日报"入口（可选，不在 v1 范围）。

### 6.4 数据缺口与失败表达

| 模式 | 触发条件 | 报告表现 | 退出码 |
|---|---|---|---|
| `normal` | 核心数据全部达到期望 as-of | 正常颜色徽章；结论全量 | 0 |
| `degraded` | 1–2 个核心指标异常/缺失 | 红色横幅"数据降级"；缺口表置顶；受影响段落加"数据缺口"chip；前瞻只写条件情景，不做方向判断 | 0（但 JSON 标记） |
| `insufficient` | ≥3 个核心指标缺失，或更新整体失败 | 生成"数据不可用公告"HTML：只有 freshness/gaps/日历，无结论；明确"今日不出判断" | 2 |
| `aborted` | 交易日历无法判定、数据目录不可读、锁超时且 strict | 不生成 HTML；写 `ERROR.json` + 日志；调度报警 | 2/3 |

**核心指标**（用于完整性判定）：`WRESBAL`、TGA 日值、`RRPONTSYD`、`SOFR`/`EFFR`、`SRF`、`WALCL`。外围指标（行情、ETF、加密、曲线）缺失只降级、不阻断。

**表达规则**

- 每个图表/表格都有 `as-of` 与 `status`（正常 / 设计内滞后 / 异常 / 缺失）。
- 缺口必须写"期望时点 / 实际时点 / 滞后工作日 / 影响 / 建议动作"。
- 不用前值填充、不插值、不用占位数字；缺失就显示 `—` 并说明原因。
- 若核心指标异常，报告结论区必须写"数据完整度 X/Y；以下判断置信度下降"；不得静默用陈旧数据得出结论。

## 7. 调度与并发

### 7.1 调度方式决策

| 选项 | 做法 | 与项目约定 | 建议 |
|---|---|---|---|
| A（默认） | 外部调度器在 **15:40 北京**调用 `hourly_update.sh daily`，成功后**链式**调用日报 `--once`（`daily && report`） | 仓库只提供 cron/launchd 样例，不自动安装 | **采用**；链式调用天然满足"更新完成才出报告" |
| B | 前台常驻 `hourly_update.sh loop`（只服务子日频）+ 手动/定时触发 `daily` | 符合 D-TGA-09"不装系统服务" | 有人值守时可用；12 点前需人工确认批次 |
| C | 把日报逻辑塞进 `hourly_update.sh` | 耦合数据更新与报告 | 不推荐 |

**推荐 A + 可选 B**：`daily` 子命令负责全量刷新、硬超时与状态文件；调度器把日报接在 `daily` 成功之后，或在 16:00 单独触发但先读 `daily_update.json`。仓库提供 `docs/ops/` 样例（plist / crontab 行），由用户决定是否安装；不在仓库内自动注册系统服务。

### 7.2 与 `hourly_update.sh` 的关系

- `hourly_update.sh` 仍是**唯一的数据更新器**，现在有三个子命令：
  - `daily`：15:40 全量批次（报告的主数据源），完成后写 `var/run/daily_update.json`；
  - `loop`：整点 `--due-only`，只为 1h/4h 等子日频数据集保留（加密等），不参与日报 T-1 基准；
  - `run`：手动一轮全量，用于补缺口/抓修订。
- 日报的生成时点在 16:00 北京（08:00 UTC），批次在 15:40 已完成；日报**以 `daily_update.json` 为前置条件**，不再等待"08:00 整点轮询"。
- 批次 `status=ok/partial`：正常出报告；`partial` 逐数据集标注 as-of 与失败项。
- 批次 `timeout/blocked/failed/缺失`：用最近一次成功批次，报告顶部显式写"今日批次未完成，以下基于 YYYY-MM-DD 成功批次"；不静默用陈旧数据出结论。
- 兜底刷新只在批次失败或某序列未覆盖时执行；16:00（08:00 UTC）重新抓 EFFR/SOFR 仍是 T-2，不会把 checkpoint 推成"伪 T-1"。

### 7.3 并发写锁

已实现（`scripts/hourly_update.sh`）：

- **单例锁** `var/run/hourly-update.lock`（mkdir + pid，loop 生命周期持有）：只防止两个 `loop` 并发，不承担写互斥。
- **写锁** `var/run/update-write.lock`（mkdir + pid，**每轮/每批短持有**）：`loop` 每轮、`run` 每次、`daily` 整批各自获取；等待上限 `LOCK_WAIT_SECONDS=300`，陈旧锁按 pid 存活状态自动清理。
- macOS 无 `flock` 命令，因此沿用项目已有的 mkdir+pid 原子锁语义，而不是引入外部依赖。
- `daily` 批次拿不到写锁 → `status=blocked`、退出 3，报告走"最近成功批次 + as-of 标注"路径。
- 日报读取 facts 时也获取同一把写锁（最多等 300s），读到稳定快照后释放；拿不到则只读并在报告中标注 `concurrent_update`，避免跨数据集读到混合轮次。

> **验收**：并发测试——同时启动 `hourly_update.sh loop` 与 `hourly_update.sh daily`，`daily` 要么等到轮次结束成功执行，要么在 `LOCK_WAIT_SECONDS` 后明确 `blocked`；不得出现两个进程同时写 canonical，也不得让 `daily` 被整小时循环锁永久挡在外面。

4. **诚实标注**：旧调度的 T-3 情形（报告 08:00 UTC 读前一天 09:00 UTC 抓取的版本，而那时只能看到 T-3）未能在本环境直接复现——最近的整点轮询并非 09:00，且当天为周日。T-3 的判定来自 `release_time` 与调度时刻的推导，非实测快照；交易日连续 3 天探测仍列在 Phase 0。

## 10. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 把 T-2 数据写成"当前"，误导读者 | freshness 表 + 时点词校验 + 每段 as-of；T-2 明确写为 16:00 报告的结构性上限 |
| 批次超时/部分失败，报告读到混合 as-of | `daily_update.json` 闸门 + 逐数据集 checkpoint as-of + `partial/timeout` 时用最近成功批次并显式标注 |
| 日报与整点轮询并发写 | 单例锁与写锁分离；写锁每轮短持有（`var/run/update-write.lock`，mkdir+pid，等待上限 300s）；报告读 facts 也持锁 |
| 全量刷新 378 个 dataset 超出 20 分钟窗口 | `daily` 默认只刷日报输入源（140 个，实测 316.9s）；`DAILY_SOURCES=all` 走 `--due-only`，CCXT 等交给 `loop` |
| LLM 编造数字/因果 | 数字白名单 + 引用校验 + 风险 ID 白名单 + 模板回退 |
| 每天内容雷同 | 昨日计分卡 + 变化引擎 + 编辑日历 + 新颖度检查 + 可证伪要求 |
| 周频数据导致"周二–周四没新料" | 明确 cadence：周二–周四讲资金面/TGA/拍卖；周五/Monday讲新 H.4.1/H.8；不硬凑 |
| 报告产物膨胀/不可复现 | 只保留 HTML+MD+JSON；JSON 存 facts_hash/run ID/model/prompt_hash；运行产物不入 git |
| 2027 后日历失效 | 调度器捕获 `ConfigError` 并非零退出；年度维护清单 |
