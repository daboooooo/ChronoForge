金融多源数据系统

编码前最终整体设计审计要求

Audit Type: Final Design Readiness Audit / Implementation Gate
阶段： 架构与设计完成 → 底层模块编码与测试实施之前
目标： 审计完成后冻结架构与核心设计，正式进入并行 Coding Agent 实施阶段

⸻

1. 审计目的

本轮审计是系统进入底层模块编码之前的最终整体设计审计。

当前项目已经完成：

1. 系统总体架构设计
2. 模块划分
3. 数据模型设计
4. 数据源设计
5. 数据获取设计
6. 数据存储设计
7. 数据处理设计
8. 接口设计
9. 工程约束
10. 第一轮设计审计
11. 根据第一轮审计结果完成设计修改

因此，本轮审计不再以“提出更多可能的设计方案”为主要目标，而是判断：

当前全部设计内容是否已经形成一个内部一致、边界清晰、可实现、可测试、可验证、可并行开发的完整工程设计。

本轮审计结束后：

* Critical / High 风险必须清零；
* 核心架构不得再存在未决方案；
* 核心数据 Contract 必须冻结；
* 核心 API Contract 必须冻结；
* 核心数据一致性规则必须冻结；
* 底层模块可以进入编码；
* Coding Agent 不应再被要求自行做关键架构决策。

⸻

2. 本轮审计的核心判断

审计最终必须回答一个问题：

如果现在把底层模块分别交给多个互不沟通的 Coding Agent，仅依赖现有设计文档、项目约束和接口 Contract，他们是否能够独立完成实现、测试和验证，而不会因为设计歧义产生互相冲突的实现？

必须同时满足：

Architecture
      ↓
System Design
      ↓
Module Design
      ↓
Data Contract
      ↓
API Contract
      ↓
Implementation Contract
      ↓
Test Contract
      ↓
Acceptance Criteria

形成完整闭环。

任何一个核心模块出现：

Design ambiguity
Contract ambiguity
Missing invariant
Missing error behavior
Missing test boundary
Undocumented dependency

都必须视为设计尚未冻结。

4. 审计原则

4.1 不重新设计

本轮不是重新进行架构设计。

审计人员可以指出：

* 错误
* 缺失
* 矛盾
* 不可实现
* 不可测试
* 不合理依赖
* 数据风险

但是不能因为“还有一种更喜欢的设计”就要求重新设计。

只有存在明确工程风险时，才要求修改设计。

⸻

4.2 Evidence-Based Review

每一个审计结论必须基于：

* 当前设计文档
* 明确的工程原则
* 数据源实际 API 行为
* 数据存储机制
* 明确的数据模型
* 测试要求

不得使用：

“一般应该这样。”

作为唯一依据。

对于关键设计决策必须回答：

Why?
Based on what?
What constraint does it satisfy?
What failure does it prevent?

⸻

4.3 Implementation Readiness First

本轮重点不是评价设计“是否漂亮”，而是评价：

能否马上实现。

14. Checkpoint Safety Audit

Checkpoint 必须满足：

    ≤
last durable + validated data boundary

绝不允许：

必须审计：

* checkpoint 创建
* checkpoint 更新
* checkpoint 回滚

* checkpoint 损坏
* checkpoint 与数据提交的一致性

15. Atomic Commit Audit

数据写入和 checkpoint 更新必须形成明确的一致性机制。

必须避免：

↓
write data
↓
process crash

导致：

checkpoint says success
but data is missing

推荐逻辑：

Fetch
 ↓
Validate
 ↓
Write temporary
 ↓
Verify
 ↓
Atomic Commit
 ↓
Advance Checkpoint

具体实现可以不同，但必须证明不存在 checkpoint 超前问题。

57. 审计问题严重等级

CRITICAL

可能导致：

* 数据丢失
* 数据损坏
* 历史数据错误
* checkpoint 错误
* 不可恢复
* 不同模块产生不同数据语义
* 无法可靠验证数据正确性

必须修改后才能进入编码。

⸻

HIGH

可能导致：

* 模块无法独立开发
* 大量返工
* 接口不兼容
* 测试无法验证核心行为
* 并行开发冲突
* 严重性能问题

必须解决后进入编码。

⸻

MEDIUM

不会阻止底层编码，但需要记录并安排处理。

⸻

LOW

文档质量、表达或非核心工程改进。

⸻

58. 本轮审计禁止的问题

审计人员不得提出以下类型的“阻塞意见”：

“我个人更喜欢另一种架构。”

“未来可能会需要……”

“如果以后规模变大……”

60. Final Gate

最终审计结果只能属于以下三个状态：

READY

满足：

Critical = 0
High = 0
Core Ambiguity = 0

可以：

冻结设计并进入底层模块编码与测试实施。

⸻

READY WITH WARNINGS

满足：

Critical = 0
High = 0

但存在 Medium / Low 问题。

允许进入编码，但必须：

* 建立 Issue
* 指定责任模块
* 指定处理阶段
* 明确不影响当前 Contract

⸻

NOT READY

存在：

Critical > 0
or
High > 0
or
Core Contract Ambiguity > 0

不得进入正式编码阶段。

⸻

61. 本轮审计的最终原则

本轮审计完成后，设计应该达到：

Design Frozen, Implementation Open.

也就是说：

设计决策冻结，但实现工作正式开始。

Coding Agent 可以自由决定：

How to implement

但不能重新决定：

What the system means

特别是：

Data Contract
API Contract
Storage Semantics
Incremental Semantics
Checkpoint Semantics
Continuity Rules
Error Semantics
Module Boundaries

必须已经确定。

⸻

62. 最终批准标准

本轮审计只有在以下命题全部成立时才能批准：

1. 架构是完整的。

2. 模块边界是明确的。

3. 数据语义是统一的。

4. 接口 Contract 是稳定的。

5. 数据获取支持可靠增量。

6. 数据存储支持安全增量提交。

7. 数据连续性可以被验证。

8. 数据错误可以被检测。

9. 数据缺失不会静默发生。

10. 任务失败可以恢复。

11. 重复执行不会破坏数据。

12. Backfill 与 Incremental 具有一致语义。

13. 历史数据修订具有明确处理机制。

14. 核心不变量都有对应测试。

15. 每个底层模块都可以独立交给 Coding Agent。

16. Coding Agent 不需要重新做架构决策。

17. 测试能够证明实现符合设计，而不仅仅是证明代码可以运行。

18. 不同 Coding Agent 的实现最终能够通过 Contract 无冲突地集成。

⸻

63. 审计完成后的工程状态

通过最终审计后，项目正式进入：

                    DESIGN
                      │
                      ▼
              FINAL AUDIT
                      │
                      ▼
              DESIGN FREEZE
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Agent A      Agent B      Agent C
       Module A     Module B     Module C
          │           │           │
          ▼           ▼           ▼
        Tests       Tests       Tests
          │           │           │
          └───────────┼───────────┘
                      ▼
               CONTRACT TEST
                      │
                      ▼
                INTEGRATION
                      │
                      ▼
             SYSTEM VALIDATION

从这一阶段开始，如果发现核心 Contract 本身存在问题，不应由 Coding Agent 擅自修改，而必须回到 Design Change Process。

这意味着：

Coding Agent
    │
    ├── Implementation Bug
    │       → Agent Fix
    │
    ├── Test Bug
    │       → Agent Fix
    │
    └── Design / Contract Problem
            → Design Review
            → Controlled Change
            → Contract Version

从而避免项目进入：

“边写代码、边重新设计架构、边修改接口、边互相兼容”

的失控状态。
